1. Contexto y motivación

La arquitectura original planteaba un monorepo con frontend Astro, backend FastAPI (Python) y TimescaleDB en Docker, con un API Python en Railway. Al revisar las necesidades reales de Antimahue —inventario y punto de venta para una sola tienda— ese stack resultó sobredimensionado:

  • El backend Python del proyecto de referencia (iot-assistant) existe por dos razones que Antimahue no tiene: reconocimiento de componentes por imagen (IA de visión) e ingesta de telemetría IoT.
  • TimescaleDB resuelve series temporales de sensores; las ventas del día son una agregación SQL normal.

Todo lo que Antimahue necesita del servidor se resuelve en TypeScript + Supabase, sin Python, sin Railway y sin Docker en producción.

2. Seguridad como principio rector

No-negociables de seguridad
Antimahue maneja dinero (de Angélica y de sus clientes) y datos personales de terceros (clientes, proveedores, RUT en los DTE). La seguridad es un principio rector del proyecto, presente en cada fase de implementación, no una tarea de endurecimiento al final.
Cliente no confiable

La autorización real se aplica en RLS/Postgres, nunca solo en el JavaScript del navegador.

RLS deny-by-default desde el día 1

Todas las tablas del esquema public tienen RLS activo desde el primer día.

Separación de claves

La clave anon es pública y opera solo con RLS; la service_role nunca entra al bundle del cliente.

Integridad server-side

Totales, montos y stock se validan con constraints de Postgres + funciones RPC. La venta es una transacción atómica.

Trazabilidad y auditoría

Toda operación sobre dinero o stock queda registrada con autor, fecha y detalle.

PIN endurecido

Rate-limiting y bloqueo temporal ante intentos fallidos. El PIN protege un token ya emitido; no es la credencial en sí.

Cadena de suministro

pnpm v11 con minimumReleaseAge + allowBuilds vacío + lockfile + auditoría periódica.

Transporte y sesión

HTTPS siempre; tokens con expiración corta + refresh; manejo seguro del token en el dispositivo.

Datos personales

Minimización de datos y cumplimiento de la normativa chilena de protección de datos personales.

Continuidad operativa

Respaldos y plan de restauración definidos desde el inicio; perder datos equivale a perder dinero.

Mínimo privilegio

Claves, roles y políticas con el menor nivel de acceso necesario.

Cada especificación, diseño y conjunto de tareas de cada cambio incluye su dimensión de seguridad explícita; el diseño incorpora un modelo de amenazas; antes de cada merge significativo se ejecuta una revisión de seguridad.

3. Arquitectura propuesta

Capa Tecnología Responsabilidad
Frontend SPA: Vite + React 19 + TypeScript + Tailwind v4 + vite-plugin-pwa Toda la interfaz: PIN, dashboard, venta, escáner, catálogo, paletas de color. App privada detrás de login.
Backend Supabase (PostgreSQL + Auth + Storage + RLS + PostgREST + Edge Functions) Datos, autenticación, almacenamiento de imágenes, API REST automática.
Región DB Supabase en São Paulo (sa-east-1) Menor latencia desde Chile (~70 ms medidos; EE.UU. ~150 ms).
Hosting Cloudflare Pages (confirmado en fase de diseño) Sirve el bundle estático desde el edge (~17 ms desde Chile). Decisión reversible.

Por qué SPA y no Astro

La aplicación principal es 100 % privada, sin contenido público ni SEO. El portal público y la comunidad serán una aplicación separada. Una aplicación POS interactiva detrás de login es el caso natural de una SPA. Astro agrega complejidad de SSR/hidratación sin beneficio. El handoff de diseño ya recomendaba React + Vite → PWA.

Lógica server-side sin Python

  • Parsing de DTE XML (Tipo 33/46/39) → función en TypeScript (fast-xml-parser) o Edge Function de Supabase.
  • Asistente de armonía cromática → cálculo HSL/CIELAB en el cliente (determinista, sin IA).
  • Escaneo de código de barras → cliente (Barcode Detection API).

5. Gestión de dependencias: pnpm v11 (obligatorio)

El proyecto usa pnpm v11 como gestor de paquetes. Es una decisión de seguridad —parte del principio rector— y es mandatoria:

ConfiguraciónPropósito
minimumReleaseAge: 1440 No instala paquetes publicados hace menos de 24 h. Defensa directa contra ataques de supply-chain de ventana corta.
allowBuilds vacío Bloquea lifecycle scripts (postinstall), el vector habitual de ejecución de malware.
Lockfile comprometido pnpm-lock.yaml en el repositorio con versiones pineadas.
pnpm audit periódico Auditoría de vulnerabilidades en cada PR y al menos semanal.
Incidente TanStack (2026-05-11) — contexto

El 2026-05-11 se publicaron 84 versiones maliciosas en 42 paquetes @tanstack/* por secuestro del pipeline de GitHub Actions. Los paquetes afectados incluyeron @tanstack/react-router, vue-router, solid-router, router-core, react-start y router-plugin. Las versiones maliciosas se detectaron y removieron en 20-26 minutos; con minimumReleaseAge: 1440 nunca habrían sido instalables. Como alternativa sin la mancha del incidente, se eligió React Router v7 (no afectado).

7. Decisiones diferidas a la fase de diseño

  • Router exacto (React Router v7 vs TanStack Router).
  • Host de producción (Vercel vs Cloudflare Pages) — reversible, no bloqueante.
  • Estrategia del PIN (bloqueo local del dispositivo vs desbloqueo de credencial real) + mecanismo de rate-limiting.
  • Librería de estado (nanostores / zustand) y patrón del cliente Supabase.
Estado actual
Todas estas decisiones quedaron resueltas en la fase de diseño. Ver design.html para los detalles.

3

4

5
Verify — compilación, conexión con Supabase, tests de RLS y security review antes de dar el cambio por cerrado.
