Especificación: modelo de datos, RLS y RPC de dominio

Catálogo, venta, configuración y seguridad — requisitos verificables, sin UI
Fase: Especificación Estado: Completada Depende de: Propuesta (D1–D7 aprobadas) Cierra: REQ-SETUP-7 / V-7 de setup-stack
Principio rector heredado de setup-stack
El bundle del cliente no es confiable. Toda la autorización de dinero y stock vive en Postgres —RLS, CHECK y funciones RPC—, nunca solo en JavaScript. Esta especificación entrega lo que setup-stack dejó explícitamente diferido: los GRANT y las políticas con auth.uid() sobre tablas de negocio.
Dominios de esta especificación:
  • Catálogo (4 requisitos)
  • Venta (4 requisitos)
  • Configuración (3 requisitos)
  • Seguridad (5 requisitos)
Dominio: catálogo

Datos del catálogo de productos: columnas visibles para el vendedor, aislamiento de costo y proveedor en una tabla separada (decisión D2), atributo de color estructurado (D5) y la función que escribe ambas tablas en una sola transacción.

REQ-DM-CAT-1 Columnas de productos seguras para el vendedor MUST

La tabla productos contiene únicamente columnas visibles para cualquier rol. costo y proveedor_id no existen ahí — se movieron a producto_costos (D2). El stock nunca puede quedar en negativo.

REQ-DM-CAT-2 producto_costos — tabla 1:1 solo para administrador MUST

producto_costos(producto_id uuid PK/FK → productos.id, costo integer NOT NULL, proveedor_id uuid NULL → proveedores.id, updated_at). El costo es integer CLP (moneda sin decimales en Chile) — alineado con la decisión de dinero del diseño. La exposición de lectura y escritura es exclusiva para el administrador (detalle en el dominio seguridad, REQ-DM-SEG-3).

Escenario: un costo por producto
Dado que producto_id es PK y FK a productos.id
Cuando se inserta una segunda fila con el mismo producto_id
Entonces Postgres rechaza la clave duplicada
REQ-DM-CAT-3 Tabla proveedores MUST

proveedores(id uuid PK, nombre text NOT NULL, contacto text NULL, telefono text NULL, created_at). Misma exposición admin-only que producto_costos.

Escenario: proveedor con datos de contacto
Dado una fila creada con nombre y telefono
Cuando un administrador la lee
Entonces ambos campos están presentes
REQ-DM-CAT-4 Color estructurado desde el día 1 SHOULD

color_nombre text NULL + color_hex text NULL CHECK (color_hex ~ '^#[0-9A-Fa-f]{6}$'). Ambas columnas nulables — etiquetar un color nunca bloquea la creación del producto.

Escenario: producto creado sin color
Dado que ambas columnas quedan en NULL
Cuando crear_producto se ejecuta sin campos de color
Entonces la inserción se completa sin error
Escenario: hexadecimal inválido rechazado
Dado el CHECK sobre color_hex
Cuando se intenta un valor como "azul" o "#12"
Entonces Postgres lo rechaza por violación del constraint
REQ-DM-CAT-5 RPC atómica crear_producto / actualizar_producto MUST

Función SECURITY DEFINER (SET search_path = '') que escribe productos y producto_costos en una sola transacción. Un producto con datos de costo no puede quedar en productos sin su fila correspondiente en producto_costos, ni al revés.

Escenario: costo inválido revierte toda la escritura
Dado que crear_producto se llama con un costo negativo
Cuando la función se ejecuta
Entonces la transacción se revierte completa
Y no queda ninguna fila huérfana en productos
Dominio: venta

Ciclo de vida de la venta: ventas/venta_items con precio congelado (D4), el ledger tipado de stock movimientos_stock (D3) y las dos funciones que hacen valer la integridad de dinero y stock del lado del servidor.

REQ-DM-VENTA-1 ventas / venta_items — precio congelado MUST

ventas(id, actor_id → auth.users, medio_pago text CHECK, total integer, estado text CHECK IN ('confirmada','deshecha') DEFAULT 'confirmada', created_at) y venta_items(id, venta_id, producto_id, cantidad int CHECK (> 0), precio_unitario integer). Los montos (total, precio_unitario) son integer CLP (moneda sin decimales en Chile) — alineado con la decisión de dinero del diseño. El precio_unitario se toma en el momento de la venta y no cambia si después se actualiza productos.precio_venta.

Escenario: el precio del ticket no cambia tras una actualización posterior
Dado una venta confirmada con precio_unitario = 1000
Cuando productos.precio_venta se actualiza después a 1200
Entonces la fila de venta_items sigue mostrando 1000
REQ-DM-VENTA-2 Ledger tipado movimientos_stock MUST

movimientos_stock(id, producto_id, tipo text CHECK IN ('venta','deshacer_venta','compra','ajuste'), cantidad, referencia_id NULL, actor_id, created_at). El valor 'compra' queda reservado desde ahora, aunque todavía no exista la tabla de compras — prepara el terreno para el futuro import de DTE sin tocar el contrato del ledger.

Escenario: el movimiento se escribe en la misma transacción que el stock
Dado que confirmar_venta se ejecuta para una venta
Cuando termina
Entonces productos.stock baja y existe una fila de movimientos_stock con tipo='venta' que referencia esa venta
Y ambos cambios son visibles juntos — nunca desde dos puntos de entrada distintos (riesgo R1)
REQ-DM-VENTA-3 RPC atómica confirmar_venta — stock nunca negativo MUST SEGURIDAD

Función SECURITY DEFINER que crea ventas + venta_items, descuenta productos.stock e inserta el movimiento 'venta', todo en una transacción. El total se recalcula en el servidor a partir de venta_items — el total enviado por el cliente no se usa. El stock nunca puede quedar negativo.

Escenario: stock insuficiente rechazado
Dado un producto con stock = 2
Cuando confirmar_venta pide cantidad = 5 de ese producto
Entonces la función devuelve un error
Y no se crea ninguna fila en ventas/venta_items/movimientos_stock, y el stock sigue en 2
Escenario: el total se calcula en el servidor
Dado una solicitud que envía un total distinto de la suma real de los ítems
Cuando confirmar_venta se ejecuta
Entonces el total guardado es el calculado por el servidor, no el enviado por el cliente
REQ-DM-VENTA-4 RPC deshacer_venta — deshacer suave, solo la última venta MUST SEGURIDAD

Función que verifica que venta_id sea la venta confirmada más reciente, cambia su estado a 'deshecha' (las filas se conservan, sin borrado físico — D4) e inserta un movimiento compensatorio por cada ítem, restaurando el stock. La regla «solo la última» se verifica dentro de la función, no solo en la interfaz — el cliente no es confiable.

Escenario: deshacer una venta que no es la última — rechazado por la RPC
Dado las ventas A (más antigua) y B (más reciente), ambas confirmada
Cuando se llama deshacer_venta(A.id)
Entonces la función devuelve un error
Y A.estado permanece en 'confirmada', sin efecto parcial
Escenario: deshacer una venta ya deshecha — rechazado
Dado una venta A con estado = 'deshecha'
Cuando deshacer_venta(A.id) se llama de nuevo
Entonces la función devuelve un error y no se duplica el movimiento compensatorio
Dominio: configuración

Ajustes globales de la tienda y el override de stock mínimo por producto (D6): un valor por defecto que se propaga de forma retroactiva, con un override nulable por producto que tiene prioridad cuando está definido.

REQ-DM-CFG-1 Tabla singleton configuracion MUST

configuracion(id int PK CHECK (id = 1), stock_minimo_default int NOT NULL, updated_at). Debe existir exactamente una fila para que la app resuelva el umbral por defecto. Si esa fila se siembra en la migración o se crea en la primera escritura del administrador queda a criterio del diseño.

Escenario: segunda fila del singleton rechazada
Dado que configuracion ya tiene una fila con id = 1
Cuando se intenta un INSERT con id = 2
Entonces Postgres lo rechaza (violación de CHECK o de clave primaria)
REQ-DM-CFG-2 Override nulable de productos.stock_minimo, resuelto con COALESCE MUST

El umbral efectivo en el momento de la lectura es COALESCE(productos.stock_minimo, configuracion.stock_minimo_default). No se usa un DEFAULT literal de columna — congelaría el valor al insertar y no seguiría un cambio posterior del default global (D6).

Escenario: el cambio del default global se propaga de forma retroactiva
Dado un producto X con stock_minimo en NULL
Cuando configuracion.stock_minimo_default cambia de 5 a 10
Entonces el umbral efectivo del producto X pasa a 10 de inmediato, sin ningún UPDATE sobre productos
REQ-DM-CFG-3 El override por producto tiene prioridad MUST

Un productos.stock_minimo no nulo tiene prioridad sobre el default global, sin importar cambios posteriores de este último.

Escenario: el override ignora un cambio posterior del default global
Dado un producto Y con stock_minimo = 20
Cuando configuracion.stock_minimo_default cambia de 5 a 10
Entonces el umbral efectivo del producto Y sigue en 20
Dominio: seguridad
Este dominio cierra un pendiente de setup-stack
Los requisitos siguientes entregan los GRANT y las políticas con auth.uid() que openspec/specs/setup-stack/spec.md dejó explícitamente diferidos en REQ-SETUP-7 / V-7.
REQ-DM-SEG-1 is_admin() — SECURITY DEFINER, sin recursión de RLS MUST SEGURIDAD

is_admin() RETURNS boolean, SECURITY DEFINER, SET search_path = '', lee profiles.rol sin pasar por las políticas RLS de esa misma tabla (riesgo R2, evita recursión). El permiso EXECUTE se otorga a authenticated — a diferencia de handle_new_user(), que solo se invoca desde un trigger, una función usada dentro de una cláusula USING debe poder ejecutarla el rol que hace la solicitud.

Escenario: is_admin() se usa dentro de una política sin recursión
Dado una política USING (is_admin()) en producto_costos
Cuando un usuario autenticado consulta la tabla
Entonces la política se evalúa sin error de recursión, y el permiso EXECUTE sobre is_admin() no genera error
REQ-DM-SEG-2 RLS + GRANT en toda tabla de dominio — cierra REQ-SETUP-7 / V-7 MUST CRÍTICO

Toda tabla de los dominios catálogo, venta y configuración tiene RLS activo y al menos una política — ninguna queda en deny-by-default sin políticas. authenticated recibe GRANT SELECT (más escrituras acotadas vía RPC), bajo mínimo privilegio. anon no recibe ningún grant sobre tablas de dominio (la app se autentica por PIN sobre una sesión ya autenticada, según setup-stack).

Tablaauthenticated
productos, ventas, venta_items, movimientos_stock, configuracionSELECT (+ escrituras acotadas vía RPC)
producto_costos, proveedoressolo administrador, vía is_admin() — REQ-DM-SEG-3
Escenario: REQ-SETUP-7 / V-7 quedan cerrados
Dado que este cambio está aplicado
Cuando authenticated pide GET /productos
Entonces la respuesta es 200 con filas — RLS activo y con política, no el 401 de línea base de setup-stack
REQ-DM-SEG-3 Aislamiento de costo y proveedor: [], nunca 403 (D2) MUST CRÍTICO

producto_costos y proveedores tienen políticas USING (is_admin()) WITH CHECK (is_admin()) en cada operación. Un usuario autenticado que no es administrador recibe una lista vacía al consultar estas tablas —directamente o vía embedding de PostgREST—, nunca un error HTTP.

Escenario: el vendedor no puede leer producto_costos ni proveedores
Dado un usuario autenticado con profiles.rol != 'admin'
Cuando ejecuta SELECT * FROM producto_costos o SELECT * FROM proveedores
Entonces ambas devuelven [] — cero filas, no un error 403
Escenario: la consulta embebida se degrada con gracia
Dado GET /productos?select=*,producto_costos(costo) pedido por un no administrador
Cuando se ejecuta
Entonces las filas de productos vuelven con normalidad y el producto_costos embebido llega como [], sin que la solicitud entera falle
REQ-DM-SEG-4 Toda política de escritura tiene USING y WITH CHECK MUST CRÍTICO

Toda política que permite INSERT o UPDATE define ambas cláusulas, USING y WITH CHECK. Una política de UPDATE con solo USING no existe — dejaría mutar una fila hacia un estado que quien escribe no podría haber insertado.

Escenario: UPDATE sin WITH CHECK correcto rechazado
Dado una política de UPDATE en productos acotada a authenticated
Cuando una solicitud intenta dejar la fila en un estado que viola la cláusula WITH CHECK
Entonces Postgres rechaza el UPDATE
Y una actualización dentro de los límites permitidos sigue funcionando
REQ-DM-SEG-5 La integridad de dinero y stock nunca se confía al cliente MUST

El stock no negativo, el total calculado en el servidor y la validación de medio_pago se aplican en las RPC y en constraints CHECK — nunca solo en JavaScript (principio rector, D7).

Escenario: una llamada directa a la RPC, sin pasar por la interfaz, sigue exigiendo stock >= 0
Dado una solicitud directa a confirmar_venta que no pasa por la interfaz de la app
Cuando pide más stock del disponible
Entonces se rechaza igual que si viniera de la interfaz (ver dominio venta, REQ-DM-VENTA-3)
