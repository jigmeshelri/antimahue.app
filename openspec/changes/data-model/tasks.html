Regla estructural de despliegue

Los archivos de migración van a supabase/migrations/ con prefijo de fecha estrictamente creciente respecto del último existente (20260621000000_initial_scaffold.sql). Se despliegan únicamente por push del repositorio — la integración de GitHub aplica supabase/migrations/*.sql automáticamente al fusionar. Queda prohibido aplicar estos tres archivos mediante la herramienta MCP apply_migration: registraría un timestamp de ejecución distinto del prefijo del archivo y el repositorio divergiría en silencio respecto de lo desplegado.

Contrato de actualizar_producto — decisión de esta fase, no del diseño

design.md dejó esta semántica como pregunta residual (línea 472). Se resuelve aquí: firma actualizar_producto(p_id uuid, p_producto jsonb, p_costo integer DEFAULT NULL, p_proveedor_id uuid DEFAULT NULL, p_stock_delta integer DEFAULT NULL).

  • Verifica is_admin() primero, igual que crear_producto.
  • Si el payload p_producto trae una clave stock, la función lanza una excepción. No se ignora en silencio: se rechaza. Todo cambio de stock pasa exclusivamente por p_stock_delta.
  • UPDATE productos toca solo columnas seguras para empleados, nunca stock directamente; producto_costos se actualiza con INSERT ... ON CONFLICT (producto_id) DO UPDATE.
  • Si p_stock_delta es distinto de NULL y de cero: suma el delta a productos.stock e inserta una fila movimientos_stock('ajuste', p_stock_delta) en la misma transacción — así la columna y el libro nunca se desincronizan (D3/R1). El CHECK stock >= 0 es el respaldo final si un delta negativo dejaría el stock por debajo de cero: aborta la transacción completa.

Criterio de aceptación: un payload {"stock": 999} hace que la RPC falle antes de escribir nada; un p_stock_delta = -3 sobre un stock de 2 aborta por el CHECK, y ni la columna ni el libro quedan modificados.

Implementado así (nota de la fase apply): el UPDATE productos usa CASE WHEN p_producto ? 'campo' THEN ... ELSE campo END por columna — semántica PATCH vía el operador de existencia ? de jsonb: una clave ausente del payload deja la columna intacta; una clave presente con null la limpia. El UPSERT de producto_costos usa COALESCE(p_costo, producto_costos.costo) en la rama de conflicto — un p_costo o p_proveedor_id nulo sobre una fila existente significa «sin cambio», no «borrar». Retorna void (no hay id nuevo que devolver, a diferencia de crear_producto). Nada de esto contradice spec/diseño: el diseño dejó explícitamente esta semántica de UPDATE como pregunta abierta para esta fase.

T-5.1–T-5.4 — evidencia de verificación contra prod

Cero usuarios existen hoy en producción (V1): no hay forma de mintear un JWT authenticated no-admin real. Cada tarea se cerró con la evidencia disponible más cercana, registrada en verify-report.md: el plano anon vía REST responde 401/42501 en los cinco endpoints probados (nunca lista vacía por error, siempre denegado en la capa GRANT); la matriz de privilegios (§3) confirma que authenticated no tiene DML de escritura en las tablas de solo RPC; y las políticas (§4) muestran ambas cláusulas USING + WITH CHECK presentes en toda política con capacidad de escritura. La corrida runtime completa con un JWT no-admin real — incluido el comportamiento exacto de deshacer_venta y confirmar_venta bajo ese rol — queda diferida al verify del change multi-rol/auth-pin, junto con T-5.5.

T-5.5 — diferida al change multi-rol/auth-pin, no un supuesto asumido

design.md (línea 474) afirma este comportamiento a partir de la semántica de PostgREST, pero aclara que está sin verificar contra el proyecto real. Hoy solo existe el rol 'admin' en el CHECK de profiles.rol — 0 usuarios existen en producción —, así que la prueba necesita un segundo usuario sembrado con rol distinto de 'admin', algo imposible con el CHECK actual. Se resuelve como primer ítem del verify del change multi-rol/auth-pin, cuando ese cambio amplíe el CHECK y permita sembrar ese segundo usuario. Si la respuesta llega como 403 en lugar de lista vacía, el plan alterno del diseño es separar la lectura en un endpoint RPC dedicado que ya filtre por rol.
