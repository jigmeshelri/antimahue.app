Enfoque técnico

Una SPA estática (Vite + React 19 + TypeScript + Tailwind v4 + vite-plugin-pwa) se comunica directamente con Supabase (sa-east-1) mediante @supabase/supabase-js usando solo la clave anon. El bundle del navegador es no confiable: la autorización real reside en RLS/Postgres, nunca en JavaScript.

Este documento resuelve las cuatro decisiones diferidas de la propuesta §7, produce el modelo de amenazas STRIDE-lite de §8, y mapea las 9 pantallas del handoff a un árbol de componentes feature-sliced + atómico. El alcance es infraestructura + scaffold de seguridad mínimo; las tablas de negocio corresponden al cambio futuro data-model. Cada decisión explicita su postura de seguridad.

Decisiones de arquitectura

D1 Router: React Router v7 Resuelto
OpciónAnálisisDecisión
React Router v7 (declarativo, data APIs) Maduro, ecosistema amplio, no afectado por el incidente de supply-chain del 2026-05-11; createBrowserRouter es modo nativo de SPA Elegido
TanStack Router Enrutamiento con tipos de primera clase, pero @tanstack/react-router estuvo entre los paquetes comprometidos el 2026-05-11 (propuesta §5) Descartado

Justificación: Ambos routers son técnicamente adecuados para una SPA privada de 9 pantallas. El guard minimumReleaseAge: 1440 ya neutraliza el incidente de TanStack, pero seguridad primero implica superficie de ataque mínima por defecto, no «riesgo mitigado». Elegir el paquete sin historial de incidentes es la postura conservadora que exige la propuesta §2. La ventaja en tipos de TanStack es marginal para un conjunto fijo de rutas pequeño.

D2 Librería de estado: nanostores Resuelto
OpciónAnálisisDecisión
nanostores ~1 KB, átomos agnósticos al framework, mantiene el estado de auth/sesión fuera del árbol de React y fuera de localStorage; se integra limpiamente con los listeners de Supabase Elegido
zustand Ergonómico y popular, pero su middleware persist tentaría almacenar la sesión en localStorage, un antipatrón aquí (ver D4) Descartado

Justificación: El estado a gestionar es pequeño (estado de auth, estado del bloqueo PIN, borrador de venta activa, flags de UI). nanostores mantiene el bundle liviano (objetivo PWA) y su minimalismo desincentiva persistir estado sensible en disco. Los datos de servidor (catálogo, ventas) son propiedad de Supabase, no del store del cliente.

D3 Patrón del cliente Supabase Resuelto

Un único cliente compartido en el navegador, creado a partir de VITE_SUPABASE_URL + VITE_SUPABASE_ANON_KEY, instanciado una sola vez en el módulo del cliente de Supabase en src/lib/. La clave service_role nunca se importa en el cliente (REQ-SETUP-9, V-4). La lógica server-side vive en Edge Functions de Supabase, que usan service_role desde el almacén de secretos de la función, nunca en el bundle.

// src/lib/supabase.ts — único lugar donde se crea el cliente
import { createClient } from '@supabase/supabase-js'
export const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY,
  { auth: { persistSession: true, storage: secureSessionStorage, autoRefreshToken: true } }
)

D4 Almacenamiento del token de sesión en el dispositivo Crítico de seguridad
OpciónAnálisisDecisión
localStorage (por omisión en Supabase) Persiste entre reinicios, pero cualquier script XSS inyectado puede leerlo; sobrevive indefinidamente Descartado
sessionStorage + re-auth por PIN Se borra al cerrar la pestaña; XSS todavía puede leerlo mientras la pestaña esté abierta Parcial
Refresh token en memoria + desbloqueo PIN (D5) Refresh token cifrado en IndexedDB bajo clave derivada del PIN (WebCrypto PBKDF2/AES-GCM); access token solo en memoria; PIN re-deriva la clave en cada sesión Elegido

Justificación: La PWA puede estar instalada durante semanas; un token en localStorage es el objetivo de mayor valor para un ataque XSS (amenaza T3). Se almacena el refresh token cifrado en reposo en IndexedDB, bajo una clave derivada del PIN (WebCrypto PBKDF2/AES-GCM, ver D5); el access token de corta duración vive solo en memoria. Combinado con una CSP estricta, esto limita el robo de tokens por XSS. Con autoRefreshToken: true, el access token se mantiene fresco desde el refresh token en memoria mientras la app está desbloqueada.

D5 Estrategia del PIN: «desbloquear una credencial emitida» Crítico de seguridad
Principio fundamental
El PIN no es una credencial y nunca va al servidor. Modelo: login real una vez → token vinculado al dispositivo → el PIN lo desbloquea localmente. 
REGISTRO (login real con Supabase Auth, email+contraseña):
  Supabase emite {access_token, refresh_token}
  El usuario establece PIN p
  salt = random(16);  k = PBKDF2(p, salt, 600k iters, SHA-256)  // WebCrypto
  Almacenar en IndexedDB: { enc = AES-GCM(refresh_token, k), salt, fail_count=0, locked_until=null }
  // p y k NUNCA se persisten; el plaintext del refresh_token tampoco

DESBLOQUEO DIARIO (ingreso del PIN — Pantalla 1):
  si now < locked_until: rechazar (bloqueo temporal)
  k' = PBKDF2(intento_pin, salt, 600k, SHA-256)
  intentar refresh_token = AES-GCM-decrypt(enc, k')
    éxito → fail_count=0; supabase.setSession(refresh_token); app desbloqueada
    fallo (PIN incorrecto → falla el auth tag de GCM) → fail_count++; aplicar backoff

Rate-limiting y bloqueos por intentos fallidos

4 dígitos = 10 000 combinaciones = factible de fuerza bruta. Por eso se aplica bloqueo progresivo:

Intentos fallidosAcción
1–4Permitir; incrementar contador
5Bloquear 30 s (locked_until = now+30s)
6Bloquear 5 min
7Bloquear 1 h
8+Bloquear 24 h + requiere re-login completo (email+contraseña); borrar enc

El estado de bloqueo vive en IndexedDB (cliente) Y se replica a una fila auth_attempts en el servidor en cada fallo. Defensa en profundidad: la compuerta criptográfica (GCM tag) significa que un PIN incorrecto no produce ningún token incluso sin rate-limit; el rate-limit frena el grinding en línea. Las 600 mil iteraciones de PBKDF2 encarecen el grinding fuera de línea sobre un blob de IndexedDB robado.

Preparado para múltiples usuarios sin rediseño: el registro es por fila de auth.users; el registro de IndexedDB se identifica por user.id. Agregar empleados más adelante implica nuevas filas en profiles + relajar el constraint rol + RLS por rol, sin cambiar el mecanismo de PIN.

Modelo de amenazas (STRIDE-lite)

Activos: A1 dinero/datos de ventas; A2 PII de terceros (clientes, proveedores, RUT en DTE); A3 sesiones/tokens de auth; A4 integridad del stock.

Obligatorio
T2 (RLS) y T4 (separación de claves) son bloqueantes para cualquier apply que escriba datos de negocio. Son el principio rector de la especificación hecho operativo.
IDSTRIDEAmenazaMitigaciónPrincipio §2
T1 Tampering Cliente manipulado vende a precio alterado o deja el stock en negativo Validación server-side: CHECK constraints de Postgres + RPC atómica para la venta (futuro data-model); el cliente no puede evadirla validación e integridad server-side
T2 Info disclosure Cliente anon o manipulado lee filas que no le corresponden (A1/A2) RLS deny-by-default en toda tabla public desde el día 1 (REQ-SETUP-7); consulta anon devuelve 0 filas sin política (V-7) cliente no confiable; RLS deny-by-default
T3 Tampering / Spoofing XSS roba el token de sesión (A3) CSP estricta vía _headers de CF (sin inline/eval, connect-src bloqueado); access token solo en memoria; refresh token cifrado con PIN en reposo (D4/D5); SW de vite-plugin-pwa desde el mismo origen manejo seguro del token; HTTPS siempre
T4 Elevation of privilege La clave service_role se filtra al bundle → bypass total de RLS Separación de claves (REQ-SETUP-9); service_role solo en secretos de Edge Function; check en tiempo de build: grep -r service_role dist/ vacío (V-4) separación de claves; mínimo privilegio

T8 Info disclosure Secretos comprometidos en git .gitignore cubre .env*/.envrc; solo .env.example se compromete (REQ-SETUP-10, V-5) datos personales / mínimo privilegio
T9 DoS / pérdida Pérdida de datos = pérdida de dinero (A1) Backups gestionados de Supabase; plan de restauración documentado desde el día 1 continuidad: backups y restore
