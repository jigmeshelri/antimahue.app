Especificación: Setup Stack

Infraestructura base + scaffold de seguridad — requisitos verificables
Fase: Especificación Estado: Completada Depende de: Propuesta Fuera de alcance: tablas de negocio, RLS multi-rol, transacción de venta
Principio rector de seguridad
El bundle del cliente es no confiable. La autorización MUST vivir en RLS/Postgres, nunca solo en JavaScript. Toda tabla en el esquema public MUST tener RLS activo en modo deny-by-default antes de que se escriba cualquier dato de negocio. La clave service_role MUST NEVER aparecer en el bundle del cliente.
Dominio: estructura del repositorio
REQ-SETUP-1 Layout del repositorio MUST

El repositorio debe seguir la estructura indicada. No puede existir directorio backend/, docker/ ni docker-compose.yml en la raíz.

/
├── src/
│   ├── components/
│   ├── features/        # auth, venta, catalogo, paletas, dte
│   ├── lib/             # supabase client, helpers
│   └── main.tsx
├── supabase/
│   └── migrations/      # SQL versionado (RLS incluido)
├── public/              # íconos PWA, manifest
├── openspec/
├── index.html
├── vite.config.ts
└── package.json
Escenario: scaffold verificado
Dado que el repositorio ha sido inicializado
Cuando se lista el contenido de la raíz
Entonces existen src/, supabase/migrations/, public/, vite.config.ts, index.html
Y no existen backend/ ni docker-compose.yml
REQ-SETUP-2 Toolchain de build del frontend MUST

El proyecto debe usar Vite + React 19 + TypeScript + Tailwind CSS v4 + vite-plugin-pwa. El build debe producir un bundle estático desplegable en cualquier CDN edge.

// vite.config.ts — plugins requeridos
import react from '@vitejs/plugin-react'
import tailwindcss from '@tailwindcss/vite'
import { VitePWA } from 'vite-plugin-pwa'

export default defineConfig({
  plugins: [react(), tailwindcss(), VitePWA({ registerType: 'autoUpdate' })],
})
Escenario: build de producción
Dado que las dependencias están instaladas
Cuando se ejecuta pnpm build
Entonces el código de salida es 0 y dist/ contiene index.html + assets JS/CSS con hash
Y no se reportan errores de TypeScript
Escenario: servidor de desarrollo
Dado que las variables de entorno están definidas
Cuando se ejecuta pnpm dev
Entonces el servidor inicia en http://localhost:5173 sin errores
Dominio: estrategia de dependencias
REQ-SETUP-3 pnpm v11 como gestor exclusivo de paquetes MUST

El proyecto debe usar pnpm v11. npm y yarn no deben usarse. pnpm-lock.yaml debe estar comprometido en el repositorio. La siguiente configuración es obligatoria:

# .npmrc (configuración pnpm)
minimumReleaseAge=1440
allowBuilds=
Restricción crítica
allowBuilds vacío bloquea todos los lifecycle scripts (postinstall). No hay excepciones sin una revisión de seguridad explícita.
Escenario: instalación bloqueada por paquete demasiado reciente
Dado que minimumReleaseAge=1440 está activo
Cuando se intenta añadir un paquete publicado hace menos de 24 h
Entonces pnpm rechaza la instalación con un error de edad mínima
Escenario: lifecycle scripts bloqueados
Dado que allowBuilds está vacío
Cuando se ejecuta pnpm install con una dependencia que declara postinstall
Entonces el lifecycle script no se ejecuta
REQ-SETUP-4 Cadencia de auditoría de supply chain SHOULD

El proyecto SHOULD ejecutar pnpm audit en cada PR y MUST ejecutarlo al menos semanalmente. Los CVEs de severidad crítica o alta deben bloquear el merge hasta ser resueltos o reconocidos explícitamente.

Escenario: auditoría en CI
Dado que se abre un PR
Cuando el CI ejecuta pnpm audit
Entonces el paso falla ante hallazgos de severidad crítica o alta
Y el PR no puede fusionarse hasta que se resuelva el hallazgo
Dominio: configuración de Supabase
REQ-SETUP-5 Configuración del proyecto Supabase MUST

El proyecto Supabase debe crearse en la región sa-east-1 (São Paulo). Auth, Storage y PostgREST deben estar habilitados. Las Edge Functions pueden usarse para lógica server-side.

Escenario: región confirmada
Dado que el proyecto Supabase ha sido creado
Cuando se revisa la página de configuración del proyecto
Entonces la región muestra sa-east-1
REQ-SETUP-6 Estructura de migraciones MUST

Todos los cambios de esquema deben expresarse como archivos SQL versionados bajo el directorio de migraciones. La primera migración debe crear la tabla profiles y habilitar RLS en ella.

supabase/migrations/
└── 20260621000000_initial_scaffold.sql
supabase/migrations/20260621000000_initial_scaffold.sql
Escenario: migración aplicada
Dado que el proyecto Supabase está conectado
Cuando se ejecuta supabase db push
Entonces todas las migraciones se aplican sin errores
Y supabase migration list las muestra como aplicadas
Dominio: scaffold de seguridad
REQ-SETUP-7 RLS deny-by-default en toda tabla pública MUST CRÍTICO

Toda tabla en el esquema public debe tener RLS habilitado. El estado por omisión es deny-all: sin política permisiva no hay acceso. Las políticas que otorgan acceso se añaden por tabla en cambios posteriores.

-- Plantilla: se aplica a CADA tabla del esquema public
ALTER TABLE public.{tabla} ENABLE ROW LEVEL SECURITY;
-- Sin política permisiva = deny by default (semántica de RLS en Postgres)
Escenario: anon no puede leer profiles sin política
Dado que RLS está habilitado en profiles y no existe política SELECT
Cuando una solicitud anónima consulta profiles vía PostgREST
Entonces la respuesta devuelve 0 filas (no un error — semántica deny-by-default)
Escenario: service_role omite RLS correctamente
Dado que RLS está habilitado en profiles
Cuando una llamada server-side usa la clave service_role
Entonces puede leer todas las filas (service_role omite RLS por diseño)
REQ-SETUP-8 Tabla profiles — scaffold mínimo para el MVP MUST CRÍTICO

La migración inicial debe crear la tabla profiles vinculada a auth.users. El MVP requiere exactamente 1 fila (Angélica / admin).

CREATE TABLE public.profiles (
  id         uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  rol        text NOT NULL DEFAULT 'admin' CHECK (rol IN ('admin')),
  created_at timestamptz NOT NULL DEFAULT now()
);
ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;
Restricción crítica
La clave service_role no puede aparecer en código del cliente ni en archivos .env comprometidos en git.
Escenario: fila de perfil creada al registrar usuario
Dado que un trigger o función post-auth crea una fila de perfil
Cuando se crea un usuario nuevo en Supabase Auth
Entonces existe una fila correspondiente en public.profiles
Y rol tiene el valor por omisión 'admin'
Escenario: rol no admin rechazado a nivel de base de datos
Dado el constraint rol IN ('admin') en el MVP
Cuando se intenta un INSERT con rol = 'employee'
Entonces Postgres lo rechaza con una violación de check constraint
REQ-SETUP-9 Separación de claves MUST CRÍTICO
ClaveExpuesta aUso
VITE_SUPABASE_URL Bundle del cliente URL del proyecto Supabase
VITE_SUPABASE_ANON_KEY Bundle del cliente Clave anon pública (segura solo con RLS)
SUPABASE_SERVICE_ROLE_KEY Solo servidor / Edge No debe tener el prefijo VITE_

SUPABASE_SERVICE_ROLE_KEY no debe aparecer en ningún archivo con prefijo VITE_ ni en ningún import del lado del cliente.

Escenario: service_role ausente del bundle
Dado que el proyecto se construye con pnpm build
Cuando se ejecuta grep -r "service_role" dist/
Entonces la salida está vacía (clave ausente del bundle)
REQ-SETUP-10 Secretos nunca en el repositorio MUST CRÍTICO

.env, .env.local, .envrc y cualquier archivo con valores secretos deben estar en .gitignore. Solo .env.example con valores de marcador puede comprometerse.

Escenario: .gitignore cubre archivos de entorno
Dado que .gitignore está presente
Cuando se ejecuta git status tras crear .env.local
Entonces .env.local aparece como ignorado, no como sin seguimiento
Dominio: hosting
REQ-SETUP-11 Host — decisión acotada y reversible

El bundle estático puede desplegarse en Vercel o Cloudflare Pages. La decisión se difiere a la fase de diseño y es reversible. HTTPS debe aplicarse en ambos; HTTP debe redirigir a HTTPS.

Restricción
No se debe usar un destino de hosting que requiera SSR o un proceso persistente. El bundle debe permanecer como una SPA estática pura.
Resolución
Resuelta en la fase de diseño: Cloudflare Pages. Ver design.html (D6).
Escenario: decisión documentada antes del despliegue
Dado que la fase de diseño está completa
Cuando se lee el documento de diseño
Entonces incluye la elección explícita de host (Vercel o Cloudflare Pages) con justificación
